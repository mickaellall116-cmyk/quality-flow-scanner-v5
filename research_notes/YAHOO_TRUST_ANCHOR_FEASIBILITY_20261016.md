# QF-YAHOO-TRUST-ANCHOR-FEASIBILITY-20261016 r1 — Feasibility memo

**Verdict: PARK** — the r6 privileged trust anchor (design A) is **not feasible as specified on the current host**. The design is sound on a conventional multi-user POSIX host (the r6 contract stands as a design); it fails here on three independent topology facts, each alone sufficient: (1) there is **no second uid** — every process in this environment runs as **root**, so the kernel-EPERM property the design rests on does not exist against the executor or against the modeled path adversary; (2) the **only persistent filesystem** is that same identity's own home tree — any anchor placed elsewhere is deployment-ephemeral overlay; (3) this VM is **replaced routinely**, and anchor state does not survive replacement, so every capture spanning a replacement bricks into HOLD:ANCHOR_MISSING until a human performs an out-of-band re-anchor.

**Recommended qualified-data route instead:** the **git-carried trust root** — the public ledger anchor already designed in the -18 line (`research_notes/archive_anchors/<capture_id>.json` in the public scanner repo, consumers anchored to a pinned commit, never a branch tip), with the local journal stack explicitly documented as crash-evidence under a weaker local threat model. Adoption of that route remains a separate act; this memo assesses feasibility only and authorizes nothing.

## (a) Current privilege evidence (single inspection pass, 2026-10-16)

- `id` → **uid=0(root) gid=0(root) groups=0(root)**. The agent runtime, the executor, and every tool process run as root. There is no demoted execution identity.
- `/etc/passwd` contains **no non-root login user at all** (root + system accounts + `nobody`/65534 only; no `hatch` account exists — `HOME=/home/hatch` is a root-owned tree, mode `drwxrws--- root nogroup`).
- `sudo` exists and lists `(ALL : ALL) ALL` **for root** — sudo is vestigial here; it separates nothing, because the caller already is root.
- systemd is PID 1 and functional (255), so a dedicated service identity is *creatable in principle* — but see (b): its definition and any anchor it guards cannot be made both persistent and non-root-writable on this host.
- **UNKNOWN:** whether the hosting platform offers any out-of-band privileged channel distinct from this runtime's own root shell (e.g., a console only Mike can reach). No evidence of one is visible from inside the VM, and the assessment does not assume one.
- Consequence for TR-2: "any write/rename/unlink attempt by a non-owner is a kernel EPERM" is **false in this topology**. A 0755 root-owned directory and a 0444 root-owned file are fully writable by root (CAP_DAC_OVERRIDE); the executor and the path adversary are the same uid as the would-be anchor owner. Design A's core mechanism — *replacement is impossible, not merely detectable* — cannot be instantiated. What remains achievable locally is design A's *detection* subset (hash-chained journal + fences), which is r5's machinery, already modeled to fail T9/T10 against exactly this adversary.

## (b) Minimal setup prerequisites and required authorizer

To instantiate design A as specified, ALL of the following would be required — none exists today:

1. A **second uid** (anchor/setup role) that the agent runtime cannot assume, plus a **demoted executor uid** — a platform/identity change, not a VM-local configuration. No VM-local step creates a uid the root agent cannot become.
2. A **persistent anchor location outside the executor-writable tree**. Mount evidence: `/` is an overlay (`upperdir=/run/hatch/overlay/upper`, `fsync=volatile`) — everything outside `/home/hatch` is deployment-ephemeral; `/home/hatch` itself is the one persistent mount (btrfs `/dev/mapper/rv`). An anchor under `/home/hatch` is persistent but sits in the adversary identity's own writable tree (property (1) fails); an anchor anywhere else does not survive replacement (property (2) fails). There is no third location on this host.
3. A **privileged install act per capture** and a **privileged seal act per completion** (TR-1/TR-3), each human-gated, forever — plus a **re-anchor procedure after every VM replacement** for any ACTIVE capture (TR-7).
4. Authorizer for each of the above: **Mike, separately, as production authority** (the r6 readiness separation already states privileged setup is NOT DONE and requires separate authority). This assessment does not supply that authority, and items 1–2 are not Mike's to grant by fiat — they require platform capabilities the current deployment does not expose.

Because prerequisites 1–2 cannot be met on this host, the setup estimate is not "hours of work": it is **blocked on platform change** (a runtime that offers a genuinely separate identity). A theatrical version (create a uid in the ephemeral `/etc/passwd`, anchor dir under `/home/hatch`) is estimated at a few hours plus per-replacement re-creation, and is **not recommended**: it would display the contract's shape while its load-bearing property (EPERM against the adversary) is absent — the exact failure this lane has repeatedly rejected (correct-looking form, missing substance).

## (c) Threat / rollback, and 12-trace coverage in THIS topology

The 12 modeled traces (T1, T1b, T1c, T2–T10 incl. replacement/replay classes) were modeled PASS for design A **under uid separation**. Re-scored against the inspected topology:

- **Crash/accident model** (buggy or killed executor, torn writes, races between our own processes — the failure class this lane has actually suffered, -14…-19): the r5 machinery (dir-fd fencing, hash chain, fences) still closes the traces that do not depend on the anchor namespace. This protection is real and is retained in the recommendation below.
- **Adversarial path model** (any process able to rename/replace paths — on this host, *any* process, since all are root): **T8, T9, T10 do not close.** T8's "replacement is EPERM" is void (root replaces at will); T9's coherent forged bundle can include a forged anchor, because the anchor is root-writable; T10's sealed-head freshness rests on the same root-writable anchor. The fencing-dependent parts of T1–T7 degrade from *impossible* to *detectable-at-next-fence* at best, and a root adversary that replaces journal + control + anchor coherently between fences defeats detection as modeled in r6 for the pathname design. The contract's residual statement therefore governs: **when the root is contested, nothing is provable from filesystem artifacts alone** — and on this host the root is *structurally* contested, not exceptionally.
- **Rollback / loss:** anchor loss (certain on VM replacement for any off-home placement; possible by any root process for on-home placement) ⇒ TR-7 HOLD:ANCHOR_MISSING, zero transport calls, recovery exclusively out-of-band after human adjudication of the data-tree state. Note the circular burden: re-anchoring safely requires trusting the very tree state the anchor existed to avoid trusting; adjudication effort shifts to the human, per capture, per replacement. Seal/retire have no rollback of their own (a wrongful seal is correctable only by a new privileged act under the same authority). There is no failure mode in which the executor silently proceeds — the design fails closed; what it spends is *availability*, at a rate set by the deployment cadence.

## (d) Estimate and simpler qualified-data route

**Privileged anchor (design A) on this host:** setup **not estimable as a finite task** — blocked on a platform identity capability that does not exist here; ongoing cost if approximated theatrically: 2 privileged acts per capture + re-anchor after every VM replacement + re-validation of the whole contract against a topology it no longer matches. **Not recommended.**

**Alternative (recommended): git-carried trust root.**
- Mechanism: the identity/genesis bindings and sealed chain heads are committed to the **public scanner repo** as the -18 public ledger anchor (`research_notes/archive_anchors/<capture_id>.json`, written only after verification completes; hashes/identifiers only). Restart/verification resolves the anchor from a **pinned commit** of that repo (fetched via git), never a branch tip — the discipline the -18 r2/r3 line already specified. QFAR1 publication continues to `qf-data-archive` under its existing designation; the anchor lives in the *other* repo, so the data tree never carries its own trust root.
- Why it fits this topology: the monotonic registry design B lacked ("an external monotonic registry is design A by another name," r6) already exists here — **GitHub-hosted git history**. It survives VM replacement completely (it is not on the VM), the local root adversary cannot rewrite pushed history without the account's credentials (a genuinely different trust domain, unlike any local uid), and freshness is sealed-head equality at a pinned commit rather than authenticity alone — the exact property that sank the signature design (T10).
- Cost: **zero new privileges, zero new infrastructure.** Setup is the -18 anchor discipline (already designed and modeled); per-capture cost is one ordinary commit+push act of the kind this desk already performs and verifies on every bridge post; per-completion, the seal is the anchor update commit. No per-replacement burden: a fresh VM clones and verifies.
- Honest limits: (i) verification at restart needs network access to the remote (or a previously verified local clone whose HEAD is checked against a commit hash obtained from the desk record); (ii) trust shifts to the GitHub account and to pin discipline — an account-level force-push could rewrite history, mitigated by consumers pinning commit hashes recorded in the independent bridge record (Issue #1), and by the desk rule that branch-tip-only trust is forbidden; (iii) it anchors *identity and freshness*, not local write-protection during a live run — the local r5 fencing/hash-chain machinery remains the live-run and crash-consistency layer, now honestly scoped to the crash/accident model; (iv) a hostile *local root during the live run itself* remains out of model, as the r6 contract states — with the mitigation that post-publication truth is re-verifiable from the remote anchor + archive by any fresh consumer (the -18 r3 property), so local compromise is detected at verification rather than silently canonized.
- Secondary alternative (weaker, cheapest): document the local stack under an explicitly **crash-only threat model** and treat `qf-data-archive`'s git history + QFAR1 pins as the sole system of record: a contested local state then costs a re-capture (the data is re-downloadable and attempts are budgeted) and can never corrupt research, because nothing is believed until it verifies against pins and the published container. This is strictly weaker than the git-carried anchor (no freshness root for *unpublished* state) and is recorded here as the floor, not the recommendation.

## (e) Recommendation

**PARK** the privileged trust anchor for this host. Design feasibility (abstract): established by r6. Setup feasibility (this VM): **fails** — no second uid exists or can be created with effect, the only persistent filesystem is the adversary identity's own tree, and routine VM replacement destroys any off-tree anchor state. Proceeding theatrically would reproduce, at the trust layer, the exact failure mode this lane exists to prevent.

**GO — as a direction, under its own future authorization — for the git-carried trust root** (the -18 public ledger anchor at a pinned commit) as the qualified-data route's trust anchor, with the local journal/fencing stack documented as crash-evidence. Nothing in this memo adopts that route, implements anything, or creates the anchor namespace; rev3 adoption, U-1, and any Yahoo capture remain separately gated and unauthorized.
